## 一次完整的操作路线

| 步骤 | 页面与操作 | 可以学到什么 |
| --- | --- | --- |
| 1. 查看材料 | 登录，查看已导入的示例主简历 | 先了解真实输入，模型输出仍需本人审阅 |
| 2. 收藏岗位 | 收藏“平台 API 工程师”，保存岗位原文和来源，关联主简历，再解析岗位 | 来源与个人经历分开；岗位要求不能直接变成候选人经历 |
| 3. 回答补问 | 开始准备材料，等待补问，刷新同一任务，再提交本人回答 | 缺少信息向本人核实；刷新恢复的是已保存任务与待回答问题 |
| 4. 核对建议 | 查看原文、建议和来源；接受简介建议，编辑经历，保存草稿并确认版本 | 不补造指标；采用和编辑都要本人决定；确认版本不覆盖主简历 |
| 5. 导出与投递 | 导出并下载 PDF，新建关联该版本的投递记录，展开提交时材料 | PDF 来自确认版本；投递记录保存当次提交材料 |
| 6. 练习两轮面试 | 从投递进入面试，查看问题依据，回答两轮；明确确认练习记忆，再刷新页面 | 追问针对已接受回答；练习要点仅确认后保存，不自动变成简历事实 |
| 7. 结束并回顾 | 确认结束练习，回看保留的回答与反馈 | 结束停止新生成，已有问答与反馈保留 |
| 8. 阅读恢复证据 | 查看本轮四处真实中断实验记录 | 区分业务提交和图 checkpoint；模型调用可重做，业务结果不能重复写入 |
| 9. 阅读评测报告 | 查看最终 30 案结果与 live 未验收边界 | 流程通过不代表真实模型质量通过；预算停止不是通过 |

可用的本人补问回答是：“负责 API 设计、数据库模型与接口联调，并与团队核对需求。” 编辑后的经历只采用这些已确认职责：“负责 API 设计、数据库结构与接口联调，并与团队核对需求。” 不把仅在岗位要求中出现的“维护接口文档”写成候选人经历。

两轮面试可使用以下合成回答：

1. “我用一个数据库事务保存回答和任务，并以唯一键处理重复请求。”
2. “遇到并发冲突先回滚，再读取原命令的确认结果，不再次创建任务。”

这些示例用于理解流程，不代表真实求职经历。实际使用时应替换为本人能够核对的事实。

四个中断点分别是模型返回前、草稿提交后、图 checkpoint 完成但任务终态提交前，以及回答提交但消息投递前。这些是已完成的独立故障实验，不能当成当前页面正在执行的任务。

第四个场景是回答提交后的合法续跑：attempt 保持 1，execution epoch 从 1 变为 2；它与丢失运行中 worker 后重试的语义不同。中断的外部模型调用可能产生未知 usage，不能假设成本为零或声称模型只调用一次。

live 接线已经使用真实 SDK 与本地合成 HTTP 响应验证；真实供应商模型的整套 live 调用与语义质量尚未完成验收。结构和流程通过，不证明真实生成质量。详见[任务评测报告](evaluation-report.md)。
