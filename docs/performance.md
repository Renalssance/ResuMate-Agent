# T17 性能报告

日期：2026-10-30。这里报告本次固定合成数据上的实测结果，不代表真实模型生成速度或任意部署环境。测试基线为T16 `cdde2c5`；最终负载使用冻结的完整源码快照，包含显式连接池与生产nginx。之后的解析子进程退出修复不在该快照内，也不参与此次只读API/SSE负载。

## 环境、输入与方法

宿主为Apple M4、10逻辑核、16GiB内存、macOS26.5.2；Docker29.9.2虚拟机实际10vCPU、8,319,504,384字节内存。产品容器和负载驱动全部限制在同一`cpuset=0-3`，最终内存上限总和7.5GiB（产品7GiB，driver0.5GiB）。这是同机受限容器实验，不是独立物理4核8GB服务器，也没有修改Docker全局设置。

环境包含MySQL8.4.13、两个独立API、Redis、一个worker、scheduler、Nginx1.30.6。业务GET与SSE通过真实nginx，测试专用的事件提交/计量入口直接访问API，未加入生产反代路由。模型调用为0。

初始数据恰好1用户、10,000岗位、10个Run、每Run5,000事件，共50,000事件；每条岗位原文2,232字节。每阶段预热10秒后测60秒，HTTP并发20，覆盖岗位首页/深页/搜索及Run/事件读取。原始样本、端点分布、EXPLAIN、资源限制和运行来源均保存。

事件提交后由Linux共享单调时钟记录，再与实际客户端收到对应seq的时刻相减；没有用两个未对齐系统的墙钟相减。最终900/900交付，负时间样本为0。TCP恢复数据和浏览器的offline/online恢复分别验证。

## 为什么没有继续改查询

已有`run_id/seq`唯一复合索引，事件查询EXPLAIN命中range并读取100条；每页Session关闭、500ms空轮询正确。岗位查询在此输入下包含全表扫描/排序，但最慢接口P95仍满足预算。没有增加新索引、缓存、投影层来制造“优化成果”。数据规模或访问模式改变时，再依据新的慢查询证据调整。

显式MySQL池为每进程`pool_size=5/max_overflow=5/pool_timeout=5s`；真实测试验证第11连接在5秒后拒绝，释放后可再次取得。基线两API峰值均15，最终峰值均10；结束时两API的checkout与SSE连接数均为0。最终RSS约329/326MiB，完整时间序列保存。这不证明无限期运行绝无泄漏。

## 前端与浏览器

路由改为按需加载；流式事件以100ms或100条先到者合批，减少同批重复详情/产物请求，仍保留全部有序事件和最新补问/终态。online唤醒原重连等待，不另建第二条连接。

生产主JS由816.47kB（gzip305.25kB）降为243.49kB（gzip86.26kB），分别下降70.18%与71.74%。这是主包体积，不是所有异步资源总量，也不是直接测得的首屏提速比例。没有调高chunk警告阈值。

生产浏览器首场景补测20次本地input到下一动画帧P95为12.7ms、最大13.2ms（首轮13.8ms/16ms也保留）；第二场景真实离线35.125秒后，online到最新终态DOM为33ms，恢复只建立一条新SSE，等待旧退避期限后没有多余连接。记录的是本机浏览器输入到下一帧和DOM可见性，不声称屏幕扫描输出的精确延迟。

首场景发现测试注入重复http_client以及解析子进程BufferedReader退出问题。分别修复后只重跑受影响首案，1 passed/17.7s：上传成功12条SQL事件、PDF下载81,495字节，CSP违规和页面异常均为0。两轮16张桌面/390/320、长材料、等待/错误/离线恢复截图已全部实际查看，未见横溢、遮挡或布局回归；详见[T17测试记录](learning/test-records/2026-10-30-t17.md)。没有用Python TCP重连数据代替浏览器指标。
