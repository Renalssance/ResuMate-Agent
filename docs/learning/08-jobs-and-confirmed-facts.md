# 第八课：岗位中心、用户确认与不可变事实版本

对应 T08，接续[任务工作台](07-agent-workspace.md)。本单元让岗位成为匹配与材料准备的共同入口，并建立用户可维护、任务可追溯的事实资料。设计见[T08 局部合同](../superpowers/plans/2026-10-30-t08-jobs-and-facts.md)，实际测试与截图见[T08 记录](test-records/2026-10-30-t08.md)。

## 一、业务入口可以新增，实体不必重建

项目已经有 JobDescription。岗位收藏继续写这张表，资料页、匹配页和材料工作台读同一个 ID。如果为了“岗位中心”另建一张内容相同的表，就必须再解决两份正文、两份解析状态和两个 ID 的同步。

本次真正缺少的数据只有岗位的主简历关联。新增 nullable `primary_resume_id`，保存岗位选用的本人简历；删除简历后关联清空，岗位本身仍保留。列表只返回摘要，详情才返回原文与结构化内容，历史匹配复用 MatchResult。

收藏与解析分为两个操作。收藏先可靠保存原文与来源链接；模型解析失败时，用户无需重新粘贴长文本。粘贴岗位没有文件路径，所以解析直接使用库内 raw_text，调用已有 AgentHarness 与 JobProfile 验证。不能把 `{title,text}` 冒充合法的已解析 JobProfile。

## 二、幂等必须回答“重复的业务含义是什么”

有招聘站点和站点岗位 ID 时，使用现有唯一约束 `(user_id, source_site, source_job_id)`。没有自然 ID 时，普通手工导入按本人来源 URL 与原文精确比较；无链接按本人相同原文比较。返回已有记录时不覆盖人工修改、收藏状态和主简历。

这里直接比较已有字段，没有添加内容散列。资料规模与查询用途没有证明额外哈希值得维护。没有自然 ID 的同时并发收藏也没有承诺数据库级恰好一行。

实测还暴露了 MySQL 排序规则的影响：默认字符串比较可能忽略大小写，而 URL 的路径可以区分大小写。本单元在需要精确比较的正文与来源 URL 查询使用二进制排序规则，并用普通大小写路径样例验证；没有把不相关文本字段全部改成特殊比较。

## 三、事实的身份与版本是两个概念

`fact_key` 表示一条事实的稳定身份；每个版本有独立 UUID，revision 从 1 增加。编辑是追加新版本，不覆盖原行；删除是追加带 deleted_at 的版本。历史草稿仍能解释自己当时引用的是什么。

例子：用户确认“负责 API 设计”为 v1；后来修改为“负责 API 和数据库设计”为 v2。v2 默认未确认，用户需要再次明确核对后才用于新任务。确认的是具体内容，不能因为 v1 确认过就自动信任所有后续修改。

页面允许先保存未确认内容，明确勾选后保存才标为已确认。从简历选择一段经历也只是填入待核对文本与真实来源，不会静默确认整份解析结果。

## 四、先求最新，再过滤确认与删除

这是版本查询中最容易写反的一步：

```text
正确：每个 fact_key 找最大 revision → 再筛未删除、已确认
错误：先去掉删除/未确认行 → 再找最大 revision
```

假设 v1 已确认，v2 已删除。错误查询先移除 v2，v1 就会重新出现。同样，v2 尚待确认时也不能继续把 v1 当成“当前确认事实”。

`services/profile_facts.py` 用子查询先求每个 fact_key 的最大 revision，再连接原表并应用展示条件。`includeDeleted` 只用于用户显式查看历史，普通列表和新 Run 输入不会加载删除项。

编辑请求带 `expectedRevision`。旧页面编辑 v1，但最新已是 v2 时返回 409，页面保留输入并提示刷新；数据库唯一约束进一步裁决两个同时追加 revision+1 的请求。SQLite 不提供与 MySQL 相同的行锁语义，不能仅依赖 `FOR UPDATE`。

## 五、任务开始时固定事实集合

新 Run 创建时保存 `input_versions.facts=[{factId,revision}]`，只选本人的全局事实和本次主简历的已确认当前事实。工具后续按这组不可变 ID 读取。资料更新后：

- 已存在的 Run 继续引用原版本，避免补问前后使用不同经历。
- 新 Run 重新读取最新确认版本。
- 草稿引用必须是该 Run 实际固定集合的子集，不能引用同用户但本次未读取的事实。
- 用户删除某个事实后，后续新写入的草稿不能再引用它；已存在产物保留历史解释。

普通修改与删除因此有不同业务意义。修改允许旧任务保留旧版本；删除表达撤回，新的产物写入需要拒绝该事实。原先没有保存 facts 的历史 Run 按空集合处理，不推测它曾经读过今天的数据。

T08 只固定事实集合。简历/JD 正文的完整快照、基于旧资料提示和逐字段修改建议在 T09 完成；当前时间戳变化仍提示新建任务，不能提前声称整个输入已完成快照化。

## 六、外键动作不等于业务语义

事实来源简历的外键原本是 `ON DELETE SET NULL`。数据库这样做可以保留历史事实行，但本系统又把无来源事实视为全局资料，于是删除简历 A 可能让 A 的经历进入简历 B 的任务。

这是正常删除操作产生的真实问题。修复把业务规则放进文档删除事务：先为该来源的当前有效事实追加删除版本，再删除简历；历史仍保留，最新版本已撤回，不会被误选为全局事实。无需再建一套迁移或兼容框架。

学习数据库约束时，要同时问两件事：数据库是否允许这次删除？删除后的剩余数据是否仍表达原来的业务含义？

## 七、前端合同必须与真实 HTTP 对上

首轮真实浏览器发现，界面“全部状态”传了 `status=''`，后端只接受 saved、archived 或不传，因此返回 422。单独模拟列表成功响应的组件测试无法发现这个差异。

请求层现在省略空状态；真实 Axios 查询序列化测试验证最终 URL。错误数组也不能直接传给 Error，否则用户看到 `[object Object]`；把实际校验消息转成可读提示，并保留 HTTP 状态，供事实编辑识别 409。

岗位跳转匹配和材料准备时，只携带 jdId/resumeId。目标页等本人资料加载后再预选，账号切换后旧请求不能回填旧资料。取消旧请求和忽略旧响应是不同手段，本次用身份与请求上下文判断是否还应接受结果。

## 八、测试与实际页面怎样互相补充

SQLite/MySQL 测试覆盖自然键、归属、排序、追加版本与删除规则。前端单元测试覆盖未确认保存、冲突输入保留、筛选请求与迟到响应。浏览器运行真实收藏/解析接口、真实 SQL、既有结构化模型验证和独立 Agent worker。

解析模型只替换外部 HTTP transport，保留 OpenAI 客户端、AgentHarness、schema 验证、用量记录、异步提交和 SSE。这样能发现真实 202 响应、任务完成数据和前端读取之间的错配，同时不调用付费模型。

截图来自实际运行页面。岗位页看桌面两栏、手机单列、错误和长原文；事实组件单独截图保留足够可读尺寸，同时检查它与现有资料页的衔接。每张图片实际打开检查，不以构建或宽度断言替代视觉验收。

## 源码阅读顺序与练习

先读 `services/jobs.py` 与 `routes/jobs.py`，追踪一份粘贴岗位如何成为原有资料页里的同一条记录。再读 `services/profile_facts.py`，用 v1 确认、v2 修改、v3 删除的例子解释最新查询。最后读 `agent_runs.py` 的事实集合固定与 `agent_runtime/tools.py` 的引用边界。

练习：为同一简历建立两个 Run，在两次创建之间修改并确认一条事实。观察两个 Run 的 inputVersions，解释为什么两个任务不应自动引用同一个最新 UUID。再删除来源简历，检查新任务不会把原来局部的经历当成全局经历。
