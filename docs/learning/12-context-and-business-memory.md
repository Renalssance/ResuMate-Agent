# 第十二课：上下文预算、可恢复摘要与可删除记忆

日期：2026-10-30。对应 T12。已完成确定性验收；最终通过范围以 [T12 测试记录](test-records/2026-10-30-t12.md) 为准。真实模型的摘要质量和费用归入 T13，确定性模型只能证明执行机制。

## 从一个实际问题开始

简历、岗位、匹配报告和补问答案越积越多，不能把全部历史永远发送给模型。但删消息并不等于保留了关键约束；自动摘要也可能略过“没有生产经验”“不填写没有测量的指标”。另一种问题出现在用户删除偏好后：如果旧 checkpoint 的消息、摘要或文件还含有它，任务恢复时可能继续使用已删除内容。

因此本课同时处理输入预算与撤回语义。SQL 保存业务权威材料，Deep Agents 管理可恢复的工作上下文；每次发模前从 SQL 重新构造必须保留内容。用户撤回记忆时，旧会话立即失效，worker 再删除该会话所有 checkpoint 和待写副本。

## 先区分四种数据

| 数据 | 权威来源与用途 | 本课的删除边界 |
| --- | --- | --- |
| 本次简历/JD/匹配快照 | Run 固定输入，保证重试与审阅的来源可追溯 | 删除记忆不改业务快照 |
| 已确认事实、补问答案 | 个人经历的依据，必须保留准确 ID/版本/正文 | 不把偏好当成经历来源 |
| 用户确认的偏好/练习反馈 | 影响措辞、准备重点；Run 只冻结所选记忆 ID | 删除时清空正文与来源，停止旧会话使用 |
| 消息、摘要、StateBackend 文件 | SDK 的可恢复工作副本 | 由 worker 删除整个失效 thread 的所有版本 |

同一段话可能同时存在于独立的面试记录和用户保存的记忆中。删除记忆只撤回后者，不能按全文搜索去删除原面试记录，也不能之后从原记录自动重建刚删掉的记忆。界面必须如实说明历史简历、投递版本和原面试记录仍保留。

## 容量和输出上限解决不同问题

设置新增 `context_window_tokens`，原 `max_tokens` 仍表示输出预留。旧用户的容量保持 NULL，必须按模型服务说明显式填写；模型名字相同不代表不同兼容服务有相同能力。

设置更新验证合并后的配置，例如原容量 16000、输出 4096，单独把输出改成 16000 也应拒绝。校验发生在改写 ORM 对象之前，失败后原设置仍可读，避免“返回错误但下一次提交意外保存部分值”。显式传 null 清除容量，未传该字段保留原值。个人设置不会继承服务器的密钥或容量。

Deep Agents 已预留约 5% 余量及输出空间。本课在这套预算上配置摘要，不再重复扣一遍。计数采用偏保守字符估算，覆盖系统消息、工具说明和业务必保留区；它是调度估算，不能当 tokenizer 的精确计数，更不能当账单。

必保留区本身放不下时，应在模型调用前返回 `context_budget_exceeded`。不断摘要无法解决不可缩减的内容过大，继续重试只会增加等待和费用。页面提供修正已核实容量、降低输出上限或减少资料的入口。

## 复用摘要，而不是另写一套压缩引擎

`BusinessContextMiddleware` 沿用 SDK 的 SummarizationMiddleware 名称，替换默认摘要中间件，而非再叠加第二套。主模型入口先加入从 SQL 重建的必保留区，再交给 SDK 计算预算、选择历史窗口和生成摘要。

内部摘要也是一次模型调用：它同样需要最新业务约束、预算和会话有效性检查。SDK 在摘要模型外还有自己的重试，设置 ChatOpenAI 的 `max_retries=0` 并不会移除这一层。因此检查必须在每次摘要尝试内执行；业务撤回或预算错误不能被当作暂时网络错误重试。

当前实现对锁定 SDK 的摘要 helper 有明确依赖。测试必须真正触发该 SDK 的摘要和重试，再关闭、重开磁盘 SqliteSaver 继续任务；只检查中间件配置值不足以发现升级后行为变化。

## 长材料如何仍然精确引用

长 `get_application_context` 结果返回可理解的摘要、稳定 ID 和 `/inputs/...` 文件路径。完整原件仍在 SQL 快照，StateBackend 文件只是可恢复的只读工作镜像；模型使用现有分页 `read_file` 获取需要的精确字段。没有新增任意宿主机文件读取权限。

草稿保存仍回 SQL 检查原字段 `before`、输入版本和来源引用。即使模型误读文件或提出错误来源，工作镜像也不能替代权威数据通过校验。短材料保留易读直接返回形式，长材料不会为追求一次读完而挤掉事实和约束。

这里的稳定 ID 用现有 Run/资料身份即可；没有为了追踪而给每段文本计算摘要哈希。

## 删除不是一个列表过滤条件

删除事务先按用户归属定位记忆，清空 `content` 与 `source_ref`，保留身份、类型和时间作为删除状态记录。通过 Run 冻结的记忆 ID 找到使用过它的 tailoring 会话，标记 `context_invalidated_at`。

等待和排队任务立即取消；运行中任务在下一模型/摘要/工具边界停止。旧会话禁止新的 tailoring、retry、answer 和 claim，用户从干净会话重新准备。已经发给供应商的请求无法撤回，这个时间边界必须诚实说明。

API 不打开 checkpoint 数据库。worker 在现有独占执行锁内调用 `SqliteSaver.delete_thread(session_id)`，清除整个 thread 的 checkpoints 与 writes；成功后写 `checkpoint_deleted_at`。已有恢复扫描和任务 finally 路径都能收尾。worker 停止时返回 pending，前端显示“已停止使用，旧任务副本正在清理”，刷新后才显示实际完成状态。

PDF 只读取已确认业务版本，不读取图状态。因此即使导出复用了同一 sessionId，也不能因为记忆撤回而被误取消。用明确 kind 分支表达这个实际边界，避免把所有任务套进同一错误规则。

## 审查如何发现顺序测试遗漏的错误

创建任务需要锁定“本次选择的记忆”，删除也要定位正在使用它的 Run。如果一条路径先锁 Run 再锁 Memory，另一条先锁 Memory 再锁 Run，MySQL 的两连接请求可以相互等待。顺序执行的 CRUD 测试全部通过，仍无法发现这个错误。

本课先用同步事件控制两个真实连接，复现新建/复用会话时的死锁，再统一加锁顺序。SQLite 的 `SELECT FOR UPDATE` 没有同样语义，提前读记忆不能代替写事务屏障。因此统一以现有记忆行的无值变化 UPDATE 先取得写入排他性，再读取 ID、操作会话与任务。测试同时验证 MySQL 不死锁、SQLite 不让删除漏掉刚创建任务。

另一个跨层问题是历史失败任务：删除记忆不应改写它的历史错误，但它的会话已经不能恢复。快照新增派生的 `sessionInvalidated`，在同一次 SQL 读取里返回；前端据此决定可用动作。历史事实与当前是否能操作是两个维度，不能挤进一个 errorCode。

## 把开发验证变成学习实验

1. 修改一次容量而不改输出，再只改输出，观察后端如何验证合并值；故意越界，确认旧设置仍在。
2. 为一个合成任务保存偏好，开始补问后删除。比较业务 memory 行、Session 时间戳、Run 状态和 checkpoint 数据，而不只看页面卡片消失。
3. 暂停测试 worker，查看待清理状态；恢复并执行扫描，再确认所有旧 checkpoint 版本消失。旧简历版本应仍可审阅。
4. 用长中文材料触发真实 SDK 摘要，重开 saver 后提交补问。核对最终请求中的限制、回答 actionId 和草稿来源；记录摘要次数、估算方法与前后请求大小。
5. 分别打开桌面、390px 手机截图，查看长文本换行、按钮边界、错误提示、加载和删除状态。自动断言无横向溢出只能发现部分问题，实际查看图片仍是验收的一部分。
