## 从业务问题理解 Redis

旧的登录和聊天限流保存在 Python 字典。只有一个进程时能够工作；启动第二个 API 后，同一个人可以轮流请求两个进程，获得两份配额。重启进程也会清空本地计数。这是进程内存的边界，不是字典写法的问题。

本单元把需要跨进程共享的短期状态放入 Redis，同时让业务事实继续由 SQL 保存。任务是否受理、谁拥有资料、已经保存的回答和事件序号，都不由 Redis 决定。Redis 停止时，每种能力有不同的处理：

| 能力 | Redis 的作用 | 不可用时 |
| --- | --- | --- |
| 新任务限流 | 所有 API 共用计数 | 返回 503，业务写入前拒绝 |
| 短期连接票据 | 一次性领取身份 | 返回 503；不能用本地票据替代 |
| 模型调用统计 | 缓存汇总数字 30 秒 | 回 SQL 查询 |
| 面试事件提示 | 唤醒正在等新事件的 API | 定时从 SQL 补查 |
| 已受理 Run | 向 worker 发布任务 | SQL 保留 queued，恢复后扫描投递 |

这里仍是一个 worker 执行槽。Redis 共享计数不意味着已经实现任意数量 worker 的并发执行。

## 单元一：连接与进程的生命周期

`backend/infrastructure/redis_client.py` 集中定义连接参数。API 在启动时创建异步命令客户端和独立通知客户端，在退出时关闭。同步业务函数以及 Celery 子进程使用该进程自己的同步客户端。

命令连接采用 1 秒连接超时和 2 秒读取超时，且不自动重试 INCR、GETDEL 这种有副作用的操作。若请求已经到达 Redis，但响应丢失，盲目再调用一次就可能重复记账或消费票据。调用方得到不可用错误后按自己的业务边界处理。

Pub/Sub 是等待消息的长连接，不能套用命令连接的 2 秒空闲读取超时。通知读取任务独立管理订阅，连接失败后重新订阅；退出时取消并等待该任务，随后关闭客户端。

同步连接记录所属进程 ID。Celery fork 后初始化自己的连接，不沿用父进程的 socket。这里的进程检查解决现有 worker 的实际使用方式，没有引入连接管理平台。

## 单元二：原子计数与业务副作用

`backend/middleware/rate_limit.py` 用一段 Lua 同时完成三件事：计数加一、第一次请求设置过期、读取剩余窗口时间。Redis 依次执行脚本，使两个 API 无法各自判断“这是第一次”后留下不同窗口。

当前明确采用 auth 5 次/60 秒、chat 20 次/60 秒、run 10 次/60 秒。窗口从首次命中开始；拒绝的请求不会延长窗口。认证用 IP，已登录任务用数据库确认的用户 ID。返回 429 时附 Retry-After；Redis 故障返回 503。

限流通过路由依赖执行，因此上传文件、创建 Run、出题和导出等昂贵入口在业务函数运行前完成检查。它不限制读取已受理任务、取消或回答补问。已受理任务的进度不应因新的配额限制而无法查看。

旧业务单测通过一个 tests-only 可控对象注入限流结果，继续验证各自的事务与响应。这些测试不能证明 Redis 原子性。真实跨 API 测试使用独立容器和真实客户端，不能继承该注入。

## 单元三：缓存查询结果，而不是整个页面

`backend/services/llm_settings.py` 把用量读取拆成 SQL 汇总和最近 12 次明细。汇总包含次数、Token、每日和任务分组；明细每次实时查询。原先读取全部行再用 Python 聚合的路径改为 SQL 聚合。

`DashboardCache` 只缓存用户自己的汇总，key 为 `resumate:{环境}:stats:{用户ID}`，有效期 30 秒。模型名、服务地址、错误细节和完整响应不放入缓存。写调用记录的顺序是 SQL commit → DEL；删除失败不撤销已经保存的记录，旧汇总最长依靠 TTL 失效。

路由先取得已鉴权的 user_id 和 Session 工厂，然后关闭鉴权用的请求 Session，再等待 Redis。否则即使缓存服务自己使用短 Session，原鉴权连接仍会被整个等待过程占用；这个问题由独立审查发现，并以两库先失败后通过的测试修复。

读取汇总也需要时间，因此写缓存时扣除本次查询已经花费的时间。若读取耗时超过 30 秒，就不再缓存这份结果。缓存不能把“查询开始时的旧数据”重新变成额外 30 秒的新数据。

定向测试在 SQLite/MySQL 上验证了汇总查询与详情分离；真实双 API 的 20 次交替读取进一步测得：3 条聚合 SQL、20 条 recent SQL，连同每次鉴权共 43 条。真实 Celery 子进程写入 usage 后，下一次读取得到 2 次调用/35 tokens；Redis 停机时仍从 SQL 读到 3 次/44 tokens。这不是“完全没有 SQL”，而是减少不需要每次重算的汇总。

## 单元四：一次性票据与原登录到期时间

`WsTickets` 生成随机短期票据，在 Redis 存储 userId、interviewId、authExpiresAt。消费只执行 GETDEL：拿到值的同时删除，两个 API 同时消费时只有一个可以取得身份。

票据最长保留 30 秒，还受原 JWT 的到期时间约束。即使 Redis 的整秒过期有舍入，消费时仍检查原到期时间。申请票据不能把已有登录延长。

`get_current_user` 继续返回数据库中的 User；新 `get_current_auth` 额外返回已验证 JWT 的到期时间。T20 提供服务与认证上下文；真正的面试归属路由、首帧认证和连接关闭分别由 T16/T21 接线，不能提前写成 WebSocket 已验收。

## 单元五：提示可以丢，持久事件必须找得回来

`InterviewHints` 的固定频道只广播 interviewId 和 lastSeq，不带正文或认证材料。每个 API 只唤醒自己正在等待对应面试的消费者。消费者随后从 SQL 读取，归属检查也在 SQL 上完成。

`read_interview_events` 每次创建短 Session，验证用户归属，按 seq 分页读取后立即关闭。等待下一条事件时不持有事务，避免 MySQL 的旧快照让补查一直看不到新提交。

消费者的顺序是：先登记本地等待者，再读取 SQL；之后收到提示或到达补查时间就重新读 SQL，用最后已发送的 seq 去重。本轮 tests-only consumer 在两个真实 API 之间收到提示耗时 27.98ms；断开 reader 且不发布下一条提示后，1.758s 内从 SQL 补到事件。重复提示没有重复输出。这证明提示/补查机制，并未执行 T21 的真实 WebSocket 连接与重连协议，也不是压力测试的 P95 结论。

## 测试与学习

当前服务测试先失败后实现：统计缓存 14 项缺失失败，票据/认证/事件读取 6 项缺失失败；补齐实现并连同原设置测试后 26 项通过。提示总线先 3 项缺失失败，再 3 项通过，覆盖按面试唤醒、离开后解除注册、断线重订阅和客户端关闭。

最终真实集成 7 passed / 86.52s，覆盖同库拓扑、原子计数、票据、缓存、提示、停机恢复和隔离 OOM。20 个跨 API run 请求恰好 10 个成功、10 个 429，拒绝不延长 TTL；SQL 已提交后 Redis 停机，原请求仍返回 202，重启后原 scheduler/worker 生成一份产物、一个业务 operation 和一个成功终态。低内存 Redis 的 noeviction 保留已有队列标记，新增限流/票据拒绝，缓存回 SQL。

整体验证首轮是 969 passed / 2 failed / 10 skipped；两个失败来自 eval 子进程没有注入其声明的受控限流边界，修复评测 fixture 后定向 2 passed。统计路由释放鉴权连接的独立审查修复另有 22 passed。真实浏览器 27 passed，三张桌面/手机图已查看；旧 SQLite Linux PDF 1 passed / 14.17s，中文两页、长段落跨页和页边距正确。分层结果分别记录，不把定向修复相加成“完整全绿”。

## 三次未进入业务的失败教会了什么

第一次构建在 Docker export/unpack 时遇只读文件系统，宿主剩余空间约 158MiB；第二次复用旧依赖底座发现六项包版本与当前 lock 不符；第三次依赖对齐后，三个服务同时向空共享卷 copy-up，实际发生目录冲突。三次都标记 `executed:false`，不能记作七项业务通过或业务失败。

环境恢复后，通过当前锁文件构建无下载缓存的依赖对齐层，并核对所有已安装且在 lock 中的包：版本差异为 `{}`、缺少直接依赖为 `[]`。最后将当前完整源码快照挂载运行；共享卷改为 `volume.nocopy: true`，fresh 并行启动和七场景通过。它证明当前源码及依赖组合可运行，**没有证明生产 Dockerfile 完整新构建成功**。T19 仍须将生产安装步骤采用 `uv --no-cache` 并完成 fresh 镜像交付验收。
