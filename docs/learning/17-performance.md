# 第17课：先测到瓶颈，再决定改哪里

这次性能工作保留了三个不同层次的证据：请求在什么负载下完成、持久事件何时被客户端看到、用户输入何时反映到页面。它们不能互相替代，也不能拿合成模型的速度当真实生成性能。

## 先固定环境和样本

“很快”没有测量含义。计划先规定1万岗位、5万事件、20个HTTP并发和30个SSE订阅，再固定两API、单worker及容器CPU/内存限制。负载驱动也计入同一资源预算，避免它在无限额机器上给服务加压却漏记成本。

每阶段预热10秒，再正式测60秒。报告保留P50、P95、最大值、失败数、各接口样本及原始记录。P95是95%的观测请求不超过该值，并不表示平均耗时，更不表示每个请求都达标。API与事件延迟必须用各自的起点和终点。

SQL事件的createdAt是业务时间，不一定等于事务提交完成。负载脚本用同一Linux单调时钟记录commit后时刻及真实接收时刻，再按run/seq关联；出现缺失、重复、乱序或负时间样本会失败。

## 已正确的实现不需要再优化一次

事件复合索引、100条分页、短Session、500ms空轮询原本就正确。基线已达到预算，因此不新增广播队列、缓存或索引，也不因为EXPLAIN有filesort就宣布系统不可用。最终只对明确连接池上限与nginx传输路径的变化再测一次。

连接池上限是资源预算。每API最多10条数据库连接，池耗尽时有限等待，不能让模型等待持有连接。真实MySQL测试证明第11个连接不能无限扩张，释放后又能正常取得。完整负载结束后checkout和流计数都回到0，为资源回收提供证据。

## 前端合批是一致性问题

每条事件都立刻更新页面并重新请求快照，会把一批事件放大成重复HTTP与渲染。现在最多等待100ms，或积累100条先提交，按seq顺序合并。同批只刷新一次所需详情；在途请求合并时，后到的新seq仍要触发补查。

合批不能丢终态、补问或用户草稿。切换Run、退出账号和离开页面必须让旧批次失效。测试模拟突发事件和迟到响应，先观察11个失败，再修复；已有行为测试也保持通过。没有为减小事件数而删除历史。

路由懒加载只改变何时下载页面代码，不能改鉴权、地址或滚动恢复。主包从816.47kB降到243.49kB，但学习时应区分“主包更小”和“全部下载更少/首屏更快”，后两者还需要另外测量。

## 恢复与视觉要在真实浏览器验证

浏览器离线超过最大退避后，online事件应唤醒原等待，而不是另外启动连接。测试记录真实35秒离线与恢复后DOM变化，并等旧计时器期限过去来检测重复连接。

本次生产浏览器还发现了后端子进程退出和模型测试注入两个问题；它说明单元测试与整条调用链的职责不同。具体因果、失败和修复保存在测试记录，不把所有问题统称为“浏览器偶发”。
