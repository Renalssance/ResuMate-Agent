# 第十三课：怎样证明 Agent 做对了事情

日期：2026-10-30。对应 T13，实现、stub 确定性验收与限定审查修复完成。真实模型 smoke、12 案 live 及语义审阅待共享总预算答复后执行；尚无付费调用。

## 为什么“返回成功”还不够

一个任务可能显示 succeeded，却保存了两份草稿；也可能只保存一份，但把“在测试环境测量”改成了“线上性能提升”。前一个问题能从数据库直接判断，后一个必须阅读来源与生成内容。评测因此分为确定性验证和语义审阅，不用一个总分掩盖差异。

| 问题 | 证据 | 判断方法 |
| --- | --- | --- |
| 重复执行是否产生第二份结果 | ResumeVersion、ToolOperation、artifact.created | 独立快照验证数量与引用 |
| 是否篡改主简历或自动确认经历 | 原始 Resume、ProfileFact 与最终快照 | 对比实际业务字段 |
| 建议是否引用当前任务的合法来源 | 固定 inputVersions、事实 revision、回答 actionId | 验证来源归属、版本、字段原值 |
| 是否编造技术经验或夸大效果 | 输入事实、用户回答、原始输出、最终建议 | 固定 rubric 逐项审阅并写理由 |
| 是否真的覆盖摘要/恢复 | 实际摘要调用、文件读取、checkpoint 重开 | 从运行轨迹证明，不凭案例名字判断 |

引用存在，只证明引用指向一个真实对象。它不能证明一句自然语言被该对象支持。例如原文“没有 Kubernetes 生产经历”，引用 ID 合法但写成“负责 Kubernetes 生产集群”仍然错误。

## 使用真实执行链，只替换模型

默认 stub 评测会创建独立 SQL 数据库和 checkpoint 目录，走同一 create_run、领取、执行、补问和继续链路。测试模型能确定性地产生工具调用，便于复现失败；它不需要 API Key，也不能代表真实模型质量。

live 模式使用同一组合成资料和真实模型。工具失败与重复执行由评测程序按案例注入，并明确记录注入来源；不能把人为重放说成模型主动重复。真实模型未触发预期补问、工具或摘要时，案例必须记录缺少覆盖，不能暗中换成 stub 后算通过。

每案在独立进程内先设置数据库环境，再导入项目。原因是数据库模块可能在导入时创建 engine：先导入再修改环境，仍可能连接旧数据库。命令行参数中的凭据文件只读取模型配置白名单，不能把其中 DATABASE_URL 一起带入评测进程。

## 验证器也可能写错

verify(case, output, db_snapshot) 接收普通数据，独立检查真实数据库快照，不再次调用保存草稿服务来“证明”它自身。负向测试人为加入第二版本、错误 before、跨任务回答或错误来源，验证器必须明确失败。

这类测试不是照抄实现。它们检查的是验收工具是否能识别我们最担心的错误；若连第二份草稿都发现不了，全部案例通过也没有意义。

## 费用限制必须在实际调用之前

业务 Run 与模型请求不是一对一。一次 Run 可能包含多轮工具调用、SDK 摘要、摘要重试，甚至主模型的上下文恢复请求。只数任务或主节点消息，会漏掉实际收费请求。

评测预算回调挂在实际模型层，每次请求前预留该次可发生的最高金额；供应商返回完整 usage 后再核销差额。超时、响应丢失、缺失 usage 都不能当作免费，原预留继续占用预算。余额不足时在网络前停止，未开始的案例保留为 not_run。

金额计算使用 Decimal。输入上限、全部计费输出限制、计价币种和最高适用单价分别记录；上下文字符估算只服务运行规划，不能冒充供应商账单。Qwen 的全部输出上限与工作上下文容量是不同配置，真实执行会核对其官方语义。

限费与遥测的异常策略也不同：预算判断失败必须停止请求；追踪系统不可用则仍允许业务继续。把这两种职责合在一个“忽略异常”的回调里，会使预算成为摆设。

## 追踪只记录解释问题所需的信息

Run、Session、执行代次、模型调用和工具使用共同关联 ID。保留模型名、耗时、Token 用量、受控错误、输入版本与产物 ID，即可回答“哪个任务在哪一步失败、是否重试、产生了什么”。

生产 Langfuse 采用元数据白名单，不发送完整简历、私人答案、记忆、工具参数、认证信息或原始供应商错误体。可选配置缺失时不导入 SDK；追踪不可用时业务仍可执行。当前未配置 Langfuse 凭据，不能把本地适配测试写成云端已收到数据。

本地评测使用合成资料，因此保存公开原输出和业务产物用于审阅；reasoning 正文不进入报告。合成输出也不会自动上传外部数据集。

## 开发中实际遇到的五类误判

整条经历可作为来源引用，但它的 source_refs 应取经历自身的标记。最初验证器取了父对象标记，既拒绝正确引用，也放过错误引用。四个红测分别覆盖工作经历/项目的正确标记和错误父级标记；修复只调整来源取值，没有放宽可修改字段。

attempt 和 execution_epoch 表示不同事实。模型短暂超时后重试会增加 attempt；补问回答后再次领取会增加 epoch，却不等于失败重试。验证器原先要求 attempt 永远为1，会把成功恢复误判失败。最终以真实支持的自动尝试1–3次与有效执行代次检查，并保存实际次数，不要求“从未失败”才能成功。

公开模型输出不只有文本。工具调用的名称与参数也是模型给应用的公开动作；如果只保存 content，工具专用回答可能变成空字符串。一份被后端拒绝的草稿没有数据库版本可供回看，删除临时 checkpoint 后更会丢失提案。因此评测要明确保留公开工具调用与无效调用，仍排除 reasoning 和任意供应商元数据。

“约束仍有4条”只能证明数量。“回答曾出现一次”也不能证明后面的摘要仍保留它。长上下文验收需要逐次模型请求核对基线内容和当时已存在的回答/产物；从真正注入的 SystemMessage 取证，不能误把摘要提示词里引用的旧文本当成当前生效上下文。

on_tool_end 只说明工具正常返回，不保证业务成功。真实 read_file 对不存在文件返回 ToolMessage(status='error')，初版追踪却一律标成功。该问题已通过实际 SDK 文件工具复现并修复：只检查结构化状态，记录固定错误码，不读取或上传错误正文。

这些判断来自当前代码和实测结果，而不是新增一套抽象审核框架。五类问题均已修复，相关限定复审没有剩余问题；全过程和原始失败见 [T13 测试记录](test-records/2026-10-30-t13.md)。

## 这轮实际证明了什么

最后一轮 core 为 **12 pass / 0 fail / 0 incomplete / 0 not_run**，模式为 stub，语义状态为 `not_applicable`。保存的调用记录有 56 次实际请求：48 次主模型、8 次摘要；56 次请求均有与当时 SQL 状态对应的必需上下文证明，逐案记录中的证明数也一致。

长上下文案的 18 次请求全部通过比较，其中 8 次发生于补问恢复后的 epoch 2，包含 4 次摘要；8 次保留已回答动作引用，2 次保留当时已存在的草稿引用。它实际读取文件 5 次，等待时草稿为 0，随后重新打开 checkpoint 并保存一份草稿。这证明当前运行链的约束、固定版本、事实、偏好和可用回答/产物引用没有被摘要丢失，不证明真实模型写作质量。

完整后端 751 passed / 6 expected skipped / 103.58s 是最后一轮 A/B 评测修复前的集成结果。修复后分别通过 33 项验证器测试、22 项运行器/预算测试及最终 12 案；没有把旧全量计数改写为修复后的新全量结果。实际 Langfuse 5.0.4 SDK 在关闭 tracing 时接受 agent/generation/tool 生命周期调用；未配置云端凭据，也没有云端接收证据。

## 阅读和练习

实施合同见 [T13 计划](../superpowers/plans/2026-10-30-t13-tracing-and-core-evals.md)。从 [评测入口](../../evals/README.md)依次阅读案例、fixtures、run、verifiers 与 budget，再看 runtime telemetry 接点。

建议做三次可观察的小改动：给数据库快照多加一个版本，看哪条验证失败；给缺指标回答改成“没有可靠测量”，查看建议是否仍有凭空百分比；把可用预算调低到不足一次请求，确认 calls 中没有对应网络调用，剩余案例被报告为未执行。练习结论写明模型模式，避免把 stub 的确定性输出当成模型能力。
