# 第十一课：从确认版本到可下载、可追溯的投递材料

本课承接[第十课](10-resume-review-and-conflicts.md)。[局部合同](../superpowers/plans/2026-10-30-t11-export-and-submission.md)固定接口与事务边界，[测试记录](test-records/2026-10-30-t11.md)保留每次实际结果。页面操作只是投递材料管理，不向招聘方自动发送任何内容。

## 为什么导出读取确认版本

主简历还会继续更新；某次投递需要的是当时确认的内容。导出读取 `ResumeVersion.structured_content`，不重新调用模型，也不从当前原简历或新事实拼接。用户删除原简历后，已确认版本仍可打印；失败重试也应使用原版本，而不是悄悄换用新的材料。

任务输入是版本 ID 和接受时 revision。`tailoring` 与 `resume_export` 只有两条明确分支：前者需要岗位和简历，后者需要确认版本；混用字段直接拒绝。worker 根据 kind 选择执行器，两者复用已有领取、心跳、事件、取消和重试。增加一种实际业务任务不要求建立通用插件注册系统。

## 文件和数据库不能放进同一个普通 SQL 事务

打印较慢，不能在浏览器生成 PDF 时持有 SQLite 写锁，否则 API 和心跳会等待。执行器先校验并取出冻结内容，结束短事务，再写临时 PDF。打印后重新检查当前执行权和取消状态，原子替换最终文件，写产物事件并把 Run 完成。

最终下载同时要求 SQL 中任务成功、产物引用匹配、文件存在。单纯在目录看到一个 PDF 不代表用户可以下载它。文件替换后、SQL 提交前崩溃，重放同一 Run 可以覆盖文件；数据库仍控制可见性。这是本项目实际边界下足够简单的恢复方式，无须跨文件与 SQL 的通用事务框架。

API 与 worker 必须共享持久导出目录。Compose 使用同一 `/app/data` 卷；浏览器测试使用测试独有目录。下载先鉴权，前端通过 Bearer 请求取得 Blob 再触发保存，不把令牌写进链接地址。

## 模板是数据的一个投影

模板显式列出姓名、联系、简介、教育、工作、项目、技能、奖项、证书和语言，不递归输出整个 JSON。质量标记、来源引用、审阅理由都不是简历正文。Jinja 对用户文本转义，浏览器不执行页面脚本、不加载外部资源；输入仍是结构化材料，不接受任意 HTML 页面。

本次审查暴露了实际数据差异：经历 description、独立 bullets 和独立 metrics 可以同时存在。只显示 description 会漏掉成果；另一方面，用户已经接受或编辑新描述后，再附上原 bullets/metrics 会恢复被替换的旧内容。预览和 PDF 要使用相同规则：未改经历保留独立信息，改过描述只采用用户决定后的表达。明确空字符串同样是有效决定。

## PDF 验证为什么要分两步

文本提取检查中文字符与正文是否真实写入文件、是否遗漏字段，无法证明视觉没有裁切。逐页打开最终 PDF 渲染出的图片，才能看到边距、长段落跨页、标题孤立、文字覆盖或缺字方框。反过来，一张看起来正常的图片，也不证明 PDF 具有可复制文本。

运行环境必须与部署一致。Python Playwright 版本固定对应 Chromium，Linux 镜像安装固定 Noto CJK 字体。宿主机有中文字体不能证明 Linux worker 可用。实测曾因本机代理对 Debian HTTP 连接失败导致镜像安装失败，改同官方源 HTTPS 后构建成功；没有关闭包校验。

## 提交快照与普通关联的区别

投递记录不仅保存版本 ID，也复制当时的正文、来源、版本号和提交时间。首次关联通过 `submitted_snapshot IS NULL` 的条件更新，一次写入；同一材料重复请求返回原快照，不刷新提交时间；换版本返回409。新建投递后在同一个事务关联，任何一步失败都不留下半条记录。

快照建立后，公司、状态、备注和日程仍可编辑；普通编辑不能悄悄换掉提交材料。第一次把旧投递关联到某个版本时，原简历链接同步到该版本的原文 ID，避免三个关联字段互相矛盾。

## 截图也能发现业务错误

手机截图中，新增“查看提交时材料”使操作行的后续按钮被裁到右侧；局部换行比扩大整页宽度更合适。另一次截图里，日历已经是10月30日，新投递却默认10月29日。根因是把 UTC 的 ISO 时间截成日期，丢掉了用户本地日历语义。日历日期用本地年月日；事件时间戳才用 UTC。这两项都来自真实页面，而非假想边界。

## 练习与源码

1. 先确认一个版本，修改主简历，再导出或打开投递快照；解释哪些内容应保持不变。
2. 模拟打印失败一次并重试；观察事件和下载如何在同一个任务中恢复。
3. 同时准备 description、独立要点、独立量化成果，然后清空描述；比较未修改与已修改条目的输出。
4. 在本地凌晨检查新增投递日期，区分日期与时间戳的用途。
