# 第十课：把 AI 建议变成用户确认的独立版本

本课承接[第九课](09-evidence-based-tailoring.md)。本单元的实现与实测过程保存于 [T10 测试记录](test-records/2026-10-30-t10.md)，具体合同见[局部计划](../superpowers/plans/2026-10-30-t10-resume-review.md)。

## 建议、决定和结果是三份不同的数据

模型给出的 after 是建议，用户点接受或手工编辑才形成决定，预览显示这些决定会得到的结果。如果把三者直接写进同一份原始简历，就难以撤销、解释来源，也无法判断另一个页面保存了什么。

本项目保留原始 before、after、reason 和 fact_refs。用户决定单独记录为 pending、accepted、rejected 或 edited；手工文字放 editedText。服务端从任务固定原简历重建当前版本，再应用 accepted 与 edited。拒绝和未审阅都保留原文；撤销决定只是回到 pending，不需要猜测原内容。

原 Resume 继续服务原有资料与扩展。独立 ResumeVersion 保存本次岗位材料，确认后冻结。后续 PDF 和投递快照依赖这份明确的版本，不应重新读取随时变化的主简历。

## 为什么保存只收决定

页面发送 expectedRevision 和每条建议的 ID、状态、手工文字。它不能顺带改建议来源、原文或建议 ID，也不能通过提交整份结构删除其他经历。服务校验完整的建议 ID 集合后，根据固定基底重新计算 resume。

缺信息建议不能直接接受，因为它的 after 是 null。用户可以拒绝，或明确输入自己的补充；手工补充仍保留“本人编辑”的身份，不自动升级为长期已确认事实。来源合法与内容真实的边界仍然存在，确认表示用户已审阅，不表示机器完成了事实鉴定。

## revision 如何防止两个页面互相覆盖

假设两个页面同时读到 revision=1。页面 A 保存后变成 revision=2，页面 B 仍携带 expectedRevision=1。数据库更新条件必须同时匹配版本 ID、用户、draft 状态和 revision；B 更新不到行就返回409。

先查 revision 再无条件写入仍会出错，因为两个请求可能都在任一写入前查到1。条件更新把“判断”和“写入”放进同一个数据库动作，SQLite 与 MySQL 都能执行。不需要在浏览器放全局锁，也不能只依赖某个数据库支持的 FOR UPDATE。

409 不是输入丢失的理由。前端保留本地决定，额外读取服务器最新版本，让用户选择直接使用服务器内容，或把自己改过的条目重新应用到最新版本，然后再次保存。

关键是“改过的条目”。若 A 拒绝简介建议，B 只编辑经历描述，B 的旧页面还显示简介 pending。把 B 全表单直接覆盖到 A 的新版本会抹掉 A 的决定。重新应用时比较 B 的旧保存基线，只重放经历描述；简介继续使用服务器的拒绝状态。

## 本地状态与请求返回

服务端 revision 是保存基线，本地决定是当前输入，dirty 表示两者不同。加载失败、保存失败或冲突都不自动清空本地输入。保存期间禁用编辑是一种简单明确的选择，可以避免迟到响应覆盖用户刚输入的新文字；切换版本或账号时还要阻止上一请求回填。

路由离开提示用于拦住应用内跳转，beforeunload 用于浏览器关闭或刷新。用户取消离开后应看到原输入。确认按钮只在本地已保存、所有条目已经决定时可用，后端仍独立验证相同规则，不能把按钮禁用当作业务约束。

## 从交互到视觉验收

桌面把建议与简历预览放在可比较的位置，手机使用单列，按钮和长文字允许换行。字段标签、来源正文和缺信息说明应能直接读懂；解析 source_refs、质量元数据不属于简历正文。

实际浏览器会让两个页面读取相同 revision，先后保存并产生真实409，检查输入仍在、服务器内容可见、重新应用后未改字段得以保留。除此之外还检查接受/撤销、手工填写缺信息、取消离开、确认冻结、主简历未变，以及不存在版本时的加载错误。截图保存后逐张打开，检查长内容、冲突区、按钮对齐与手机边界。

## 学习时可以改什么

先阅读业务服务里的条件更新，再找前端 dirty、服务器基线和本地决定。尝试让两个页面分别修改不同字段，理解为什么“所有字段都带在请求里”不代表“所有字段都是本地新修改”。再尝试确认后直接发保存请求，验证不可变规则确实在服务端。

## 实测教训：空字符串也是用户决定

编辑后的 description 可以明确为空，不能用“空则回退 bullets”恢复用户刚删除的内容。另一方面，未修改原文的 description 与独立 bullets 可以同时有真实信息，不能只显示前者。最终只在预览副本去掉已接受或本人编辑字段的旧要点；未改动的经历保留独立要点。两种输入分别写回归，避免一项修复损害另一项真实需求。
