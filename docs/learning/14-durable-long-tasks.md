# 第十四课：把旧长任务接入可恢复的执行链

本课对应 T14。2026-10-30 已完成实现与确定性验收：四个真实进程中断通过，core扩至24案全部通过，最终140项前端组件测试通过，20张真实页面截图已查看。完整后端旧源码断言的迁移过程与真实模型未验收边界见 [T14 测试记录](test-records/2026-10-30-t14.md)。

## 从已有代码发现需要迁移的边界

原解析、匹配、出题与回答分析由 API 进程的 BackgroundTasks 执行，进度保存在内存 Hub。关闭页面不会主动终止后台函数，但 API 重启会失去内存进度，函数也无法从业务提交点继续。T04–T07 已经建立 Run、Redis、独立 worker 和 SQL 事件，因此本单元把四类旧任务接到同一条执行链。

规划增加回答分析并非新增产品范围：阅读路由发现它实际共用原后台分支，删除分支前必须迁移。总体计划需要能根据代码事实调整，不能机械只检查最初列出的三个入口。

## 请求标识和任务标识承担不同职责

浏览器生成的 request key 用来识别同一用户重发的提交；服务端返回的 taskId 是持久 Run UUID，用来读状态、结果和事件。旧客户端曾假定两者相同，新实现要求在接受响应后切换到服务端 ID。

```text
保存输入与 Run（一个 SQL 事务）
          ↓ commit
尝试通知 Redis → worker 领取 → 计算 → 提交业务结果和事件
          ↓ 通知失败
SQL scanner 后续发现 queued，再次投递
```

Redis 投递失败不能撤销已经接受的业务请求，也不能让 API 自己再执行一遍模型。浏览器的 `Prefer: respond-async` 返回 202 与 taskId；原同步调用仍提交同一 Run，释放请求会话后用短会话等待，最多 45 秒。完成时保留原成功 JSON，超时返回明确的未完成状态与任务 ID。

阅读入口：`backend/services/background_tasks.py`、`backend/services/agent_runs.py`、`backend/routes/tasks.py`。

## 先决定业务恢复单位，再写重试代码

| 任务 | 受理时固定什么 | 恢复时检查什么 |
| --- | --- | --- |
| 上传/重新解析/保存岗位 | 文档身份、来源引用、解析方式 | 固定文档的操作与本次 Run 结果 |
| 匹配 | 一个 AnalysisJob 与有序候选组 | 每个候选已经提交的报告和操作 |
| 出题 | 固定匹配报告快照、题数 | 本次 Run 不可变的结果 |
| 回答分析 | 类型化的问题、回答与历史 | 本次 Run 不可变的结果 |

上传先保存文件与文档身份，再返回接受响应。否则重放旧处理函数会创建第二行文档。受理后解析失败或取消保留原件，用户可以重新解析；只有受理前失败清理新文件，或用户显式删除才清除原件。

匹配以一个候选为提交单位。候选一完成、候选二失败时，重试只继续候选二。对已完成候选的读取不应该依赖再次创建模型客户端。本单元的测试曾发现这一多余依赖，随后改为需要实际计算时才初始化模型。

出题有一个容易忽略的区别：用户新发一次请求可以更新当前题库，但旧任务详情必须展示旧任务当时生成的题。因此 Run.result_json 保存本次响应，刷新旧页面不能改读“当前最新题库”。

阅读：`backend/services/document_tasks.py`、`backend/services/analysis_tasks.py`、`frontend/src/stores/question.ts`。

## 原子提交要覆盖真实业务写入

业务结果、成功的操作记录、产物事件和最终 Run 状态必须处于约定的事务中。若旧 repository 已经 commit，再在外层追加操作记录，事件写入失败时业务已经存在，外层 rollback 无法撤销它。

本单元把匹配和出题 repository 的内部提交改为 flush，让调用方决定事务；图只传普通值，不把 ORM Session 或 ORM 对象放入 checkpoint。测试通过在产物事件插入时抛出异常，验证报告、题目、操作、结果是否一起回滚。

向量索引与 SQL 不是同一事务。保留按文档身份替换索引的可重放操作，以 SQL 为业务权威，不声称跨存储原子提交。实际检查还发现向量计算期间删除文档的情况，因此在计算返回后、任何索引写入前再次检查资料归属和执行权。

## 取消是执行边界，不只是按钮状态

取消通常发生在远程调用等待期间，已经发出去的请求未必能够撤回。需要在下一次模型调用、下一条检索、索引写入和业务提交之前重新检查 Run 的 epoch、取消状态与资料归属。

已经开始的模型请求可能在进程被杀后无法取得 usage。恢复可能再次调用模型，因此业务不重复不等于模型请求只执行一次；记录中必须分开写已开始次数、已知 usage 和未知 usage，不能把未知记为零。

旧 Harness 继续记录用户级 LlmUsageEvent，尚未连接 T13 的 Run/attempt/epoch 调用观测；这一边界在测试记录中保留，不能凭恢复测试宣称完整成本追踪。

## 页面恢复依赖服务端事实

本地只保存正在处理的 taskId 与必要显示上下文。页面重开后重新订阅 SQL 事件；成功结果从本次持久任务读取。当前用户的本地任务键按用户隔离，服务端每次仍验证归属。长等待返回后还要核对当前账号：A的旧出题结果不能写入B的共享store，旧请求的catch/finally也不能覆盖B的错误与加载状态。

SSE 断开代表传输断开，不代表后台任务失败。前端保留任务，按游标重连；可重试网络错误与明确的权限/协议错误分别处理。显示进度的订阅和等待最终结果的订阅各自拥有关闭函数，页面卸载不能误关仍需结果的独立请求。但这不代表未开始的上传队列可以无限延续：用户离开或切换账号后，下一份文件不能借新账号的认证开始上传。队列捕获所属账号，离开时结束未开始项；已受理Run在服务端继续。

浏览器offline事件也不一定使正在等待的流读取立即报错。因此每次连接有单独的传输控制器，offline只中断这一条传输，让持久订阅按原游标重连；主动关闭订阅再结束整个生命周期。两个关闭范围不能混为一个。

已结束任务不会因回放旧的 running 事件退回进行中。旧任务协议由同一 SQL 事件投影，终态只由 Run 生命周期生成；手动重试后也不能让历史 failed 事件结束新的订阅。

阅读：`frontend/src/services/sse.ts`、`taskResult.ts`、`activeTasks.ts`、`useDocumentParseTasks.ts` 和各业务页面。

## 为什么必须实际截图

组件测试能够证明服务端 ID 被采用、刷新会重订阅、旧结果没有被最新题库覆盖，却不会证明手机页面没有横向溢出。首次真实浏览器检查中，一个项目支持的长中文文件名把 390px 页面撑到 809px。修复了任务卡 grid 的最小宽度、标题 flex 收缩和换行，再打开桌面与手机截图查看。

后续验收继续覆盖重解析、刷新、断网、失败、取消、匹配结果和保存的题目。截图需要实际打开，观察内容是否被截断、按钮是否错位、状态是否矛盾，并保留既有米色底、棕色强调、圆角卡片、字体和间距。生成 PNG 文件本身不构成视觉验收。

最终20张截图已实际查看，还修正了终态残留50%进度、刷新后出题条件空白与题数错误、桌面任务列表拉长页面三处问题。组件断言、真实浏览器流程和肉眼查看各自检测不同错误，不能相互替代。

## 自己动手验证

1. 在确定性测试中，让第二位候选第一次计算失败。观察重试前后的候选组、报告数和模型调用数，解释为什么第一位不应重算。
2. 先生成题目 A，再显式生成 B，重新打开 A 的任务。解释“当前题库”和“本次任务结果”的读取区别。
3. 在索引计算等待时删除来源，确认返回后不会写入索引和业务成功结果。
4. 对比 worker 被杀前后的 checkpoint、Run attempt/epoch、操作行与产物行，说明哪些证据能证明业务没有重复，哪些不能证明模型没有重复收费。

这些练习使用合成数据和隔离测试库。执行命令和原始结果由测试记录提供；本课不把确定性响应的内容质量当成真实模型语义验收。
