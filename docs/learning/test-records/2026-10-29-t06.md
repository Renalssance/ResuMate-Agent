## 失败、审查与修复

1. **先有失败测试，再增加持久事件。** 生命周期测试最初读到 `[]` 而不是 queued/running/failed/retry/cancelled；事件写失败的故障注入没有触发。实现同事务追加事件后通过。新序号并发测试还覆盖事务已经打开 MySQL 读快照的情形。
2. **快照状态与游标来自不同读取时点。** 回归稳定复现 `queued / lastSeq=2`，但序号 2 已对应 running。改为一条 SQL 读取 Run、待回答动作和最大序号；SQLite/MySQL 都通过。游标重置不会再从旧状态跳过新事件。
3. **断线期间失败并重试。** 独立审查复现前端只交付 `[1,2]`，没有交付已存在的 queued/running/succeeded `[3,4,5]`。原因是沿用连接断开前的快照边界。现在每次重连刷新权威快照，仅更新判定边界，保持消费游标；`onSnapshot` 仍仅首次调用，真正游标重置才触发 `onReset`。回归得到完整 `[1,2,3,4,5]`。
4. **旧流新增认证后占用 SQL 连接。** 使用真实 Bearer 鉴权，在流内观察连接池，修复前为 `[1,1]`，修复后为 `[0,0]`。授权后主动关闭请求会话，避免两个进度/结果订阅长期占住连接。
5. **旧页面先订阅再提交不再适用。** 任务尚未绑定归属时返回 404 是正确行为。四条调用链改为 202 后的 onAccepted 回调开始订阅，保留历史回放；补充页面卸载后迟到回调不会重开连接的测试。
6. **测试本身的会话差异。** 连接释放测试最初把种子会话提交后读取过期对象时重新获取的连接算成流泄漏。统一为生产的 `expire_on_commit=False / autoflush=False` 后，再测实际订阅连接；没有通过忽略连接数掩盖问题。

独立审查报告两项实际问题（第 3、4 项），已修复并补回归；其余检查的事务、归属、增量解析与 202 订阅衔接正确。审查不是要求把所有历史路径重写一遍。

## 真实故障实验经过

先在 Redis 尚未启动时接受 Run，再由调度器扫描补投递。worker 写入草稿与 artifact.created 后阻塞；客户端以真实登录 Token 接收流并在产物事件处主动断开，任务仍保持 running。

验证心跳推进、发布重复消息后，对测试专属 worker 发 SIGKILL。重启等待真实 90 秒失联门限，恢复到 attempt=2、execution_epoch=2。最后以已收到的 seq 重新订阅：

- 全部事件序号连续，最后收到 succeeded。
- 状态事件为 queued → running → queued → running → succeeded。
- ResumeVersion、成功 ToolOperation、artifact.created 各一份。
- 连接断开没有取消任务；测试最终清理自己的容器和卷。

本实验在最后两个审查修复之前运行；这两个修复分别属于浏览器重连逻辑和旧内存 SSE，不改变实验覆盖的新 Run API / worker 路径，因此未无依据重复耗时故障实验。
