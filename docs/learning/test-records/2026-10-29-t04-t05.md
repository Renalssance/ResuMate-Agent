## 从失败到修复

1. 初始 worker 测试先遇到测试数据 kind 写错，修正为已有契约 `tailoring`；之后 8 项因领取/恢复接口未实现而失败。它们是缺失接口失败，不声称是断言已复现的并发漏洞。
2. 投递与文件锁测试最初因模块未实现而失败；实现后 T04 11 项通过。工具和 runner 的初始测试也因模块缺失失败，实现后分别 6、8 项通过。
3. 独立审查用生产 `autoflush=False` 复现：刷新 ORM 覆盖未提交 attempt，连续四次超时仍 attempt=1。补回归后改为在终态事务中决定重试与递增。
4. 复现取消遇模型超时时异常分支再次抛错，任务停留 running；统一结束事务处理取消，立即释放 Session。
5. 同 session 新 Run 仍能读取旧 files/todos/摘要。测试确实失败后，在新任务开始前通过图状态更新清理任务私有内容；同一 Run 恢复继续保留原内容。
6. MySQL 取消回归最初读到旧状态，原因是测试在 cancel_run.refresh 后仍保留可重复读事务。结束测试读取事务后再观察独立 worker 提交；未据此改动正确的生产事务。
7. 第一次 Compose 实验失败：生产构建正确排除了 backend/tests，测试 worker 无法导入。改为仅在测试覆盖文件中只读挂载测试代码。
8. 第二次实验在心跳观测处失败。定点诊断发现：容器更新至 `14:52:37`，macOS 原生连接仍读到 `14:50:22`。修正环境为 API/worker 都在 Docker Linux 内访问同一数据库；宿主机不再读取活跃 SQLite WAL。不是放宽断言或增加超时。
9. 新 Compose 配置一次缩进错误被解析器拒绝，修复后重跑；最终完整实验通过。

## 联合故障实验实际验证了什么

测试只使用合成资料和确定性模型，实际运行 Deep Agents、官方 SQLite saver、API、Celery worker、beat 和 Redis。

- 在 Redis 尚未启动时投递失败，数据库中 Run 已持久化；启动后由 15 秒扫描发现并投递。
- 检查真实 Redis transport 的 `visibility_timeout=3600`：新未确认消息不立即重投；仅对测试消息提前未确认时间后可重新消费。此检查没有等待一小时。
- 工具提交 ResumeVersion + ToolOperation 后、返回给图前暂停；确认心跳继续更新，发送真实重复消息。
- 对专属测试 worker 执行 SIGKILL，再启动 worker。等待真实 90 秒失联阈值和扫描周期，不缩短产品配置。
- 最终状态 succeeded，attempt=2，execution_epoch=2，ResumeVersion=1，ToolOperation=1，API 返回一个产物。

此次 worker 恢复来自 **SQL 扫描 + 文件锁释放 + checkpoint 重放**，不是 Redis 的一小时可见性超时自然到期。断点精确位于业务事务提交后，证明重放工具返回原结果；不承诺模型调用恰好一次。

测试容器、网络和 Redis 测试卷已由用例清理。业务数据和 checkpoint 测试证据来自临时目录，未触及原项目数据库；Docker 安装保留供后续单元使用。
